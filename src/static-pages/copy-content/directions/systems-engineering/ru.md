## Какие задачи я решаю

Я проектирую программные продукты, в которых интерфейс, API, хранилище, очереди и оборудование должны работать как одна система. Это включает границы компонентов, сохранение состояния и восстановление при сбоях.

## Проекты

![Lifecycle Messaging Platform](../../illustrations/lifecycle-messaging-platform.webp)

**[Lifecycle Messaging Platform](../../projects/lifecycle-messaging-platform/)** — Платформа сообщений с API, PostgreSQL, очередями и отдельным runtime для GSM-модемов.

**[PhotoPizza Remote](../../projects/photopizza-remote/)** — Управление поворотным столом из браузера по локальной сети.

**[Adaptive Maximo Workbench](../../projects/adaptive-maximo-workbench/)** — Демо-интерфейс для ремонтных операций; доступный путь работает только для чтения.

**[Symbiote Node](../../projects/symbiote-node/)** — Пакетный и миграционный слой для UI-компонентов и execution-engine.


## Мой вклад

В Lifecycle Messaging Platform я проектировал архитектуру продукта, потоки данных, исполнение на модемах и серверную инфраструктуру. Для проверки логики доставки я создал Digital Twin с виртуальными модемами и повторяемыми сценариями трафика; реальные отправки оставались на физических пулах.

Для PhotoPizza Remote я разработал браузерное управление поворотным столом, а позднее — управляющее ПО для оборудования на JavaScript/Espruino. В Symbiote Node я работал над пакетным и миграционным слоем между UI-примитивами и execution-engine.

## Принципы работы

Я прослеживаю путь запроса от интерфейса через сервисы, хранение и очереди до исполнителя. Для каждого участка определяю контракт и владельца. Очереди сохраняют состояние работы, а локальный Digital Twin позволяет проверять поведение, когда физическое устройство недоступно.

Adaptive Maximo Workbench — демонстрационный проект Demo / Alpha. Его публичный путь позволяет открыть заявку, посмотреть связанное оборудование и доступные действия; подключение производственной системы Maximo выполняется отдельно.
